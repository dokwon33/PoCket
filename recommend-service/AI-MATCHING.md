# AI 실증 매칭 — 왜 필요한가, 그리고 API 명세

프론트엔드가 먼저 화면과 계약을 확정하고, 백엔드가 그 계약에 맞춰 개발합니다.
프론트는 이 명세대로 동작하는 스텁을 이미 붙여 두었으므로, 엔드포인트가 나오면
환경변수 하나로 전환됩니다. 서로를 기다리지 않습니다.

---

## 1. 왜 규칙 기반으로는 안 되는가

### 산업군은 거의 아무것도 걸러주지 못한다

현재 등록된 실증 슬롯은 **91곳**, 산업군은 **8개**입니다.
칩 하나를 눌러도 평균 **11.4곳**이 남습니다. "물류"를 골랐다는 사실은
그 안에서 어디를 갈지 정하는 데 도움이 되지 않습니다.

### 정작 결정을 좌우하는 정보는 전부 자유 텍스트 안에 있다

`courses` 테이블이 가진 컬럼은 `category · price · enrollment_count · status`뿐입니다.
그런데 실증 장소를 고를 때 실제로 보는 것은 아래입니다.

| 매칭에 결정적인 정보 | 설명문에 등장 | 전용 컬럼 |
|---|---|---|
| 데이터 제공 여부 (로그·영상·센서) | 21 / 91 | 없음 |
| 설치 조건 (천장·벽면·거치) | 19 / 91 | 없음 |
| 시간대 제약 (피크타임·야간·주말) | 17 / 91 | 없음 |
| 유동인구 (일 평균 방문객) | 16 / 91 | 없음 |
| 공간 규모 (면적·좌석·층) | 16 / 91 | 없음 |
| 네트워크 (기가·유선·5G) | 14 / 91 | 없음 |

**이 중 어느 것도 조회하거나 필터할 수 없습니다.** 컬럼이 없기 때문입니다.

### 키워드 검색으로도 안 된다

전력 조건은 매칭의 기본인데, `220V`라는 문자열은 **91곳 중 단 1곳**에만 나옵니다.
나머지는 "전용선 제공", "매장 후면 전원", "별도 배선 가능"처럼 제각각 표현합니다.
유동인구도 마찬가지입니다.

```
"일 평균 방문객 480명, 좌석 42석"
"가맹 3개점 동시 적용 가능"
"진열대별 판매 데이터 일 단위 제공"
```

같은 종류의 사실을 서로 다른 문장으로 씁니다. 정규식이나 키워드 매칭으로는
잡히지 않습니다. **문장을 이해해야만 비교할 수 있습니다.**

### 요구하는 쪽도 자유 텍스트다

스타트업이 들고 오는 조건은 이런 모양입니다.

> "무인 주문 로봇을 3개월간 검증하려 합니다. 220V 전원과 유선 인터넷이 필요하고,
> 하루 방문객 300명 이상인 매장이면 좋겠습니다."

어떤 폼으로도 담기지 않습니다. 항목을 20개 만들어도 다음 스타트업은 21번째를 묻습니다.

### 결론

> **공급도 자유 텍스트, 수요도 자유 텍스트인데 시스템은 8개 칩으로만 잇고 있습니다.
> 이 간극은 문장을 읽는 모델이 아니면 메울 수 없습니다.**

AI가 "있으면 좋은" 것이 아니라, **AI가 아니면 이 정보를 쓸 방법이 없습니다.**

## 2. 엔드포인트

```
POST /api/recommend/match
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 경로가 `/api/recommend/**` 아래인 이유

API 게이트웨이가 **프리빌트 이미지**(`msa-lecture/api-gateway:1.0`)로 실행됩니다.
`docker-compose.yml`에 `build:` 지시자도, 설정 볼륨도 없어서 **새 라우트 prefix를
추가할 수 없습니다.** 이미 라우팅되는 `/api/recommend/**` 아래에 붙여야 게이트웨이를
통과합니다.

기존 `GET /api/recommend/{user_id}`와는 HTTP 메서드가 달라 충돌하지 않습니다.
다만 FastAPI에서는 `/match`를 `/{user_id}`보다 **먼저 선언**해 주세요.

구현 위치는 **recommend-service (8085)** 를 권합니다. 이미 course-service 클라이언트를
갖고 있어 슬롯 전체를 받아올 수 있고, 새 서비스를 띄우면 Eureka·게이트웨이·compose를
모두 손대야 합니다.

## 3. 요청

```jsonc
{
  "query": "무인 주문 로봇을 3개월간 검증하려 합니다. 220V 전원과 유선 인터넷이 필요하고, 하루 방문객 300명 이상인 매장이면 좋겠습니다.",
  "budget": 3000000,            // 선택 — 원 단위 정수
  "durationMonths": 3,          // 선택 — 개월
  "categories": ["BACKEND"],    // 선택 — 사전 필터, 비우면 전체
  "limit": 5                    // 선택 — 기본 5, 최대 10
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|:---:|---|
| `query` | string | O | 1~1000자. 공백만 있으면 400 |
| `budget` | integer | X | 원 단위. `price`와 같은 축 |
| `durationMonths` | integer | X | 1~24 |
| `categories` | string[] | X | `courses.category` enum 값 |
| `limit` | integer | X | 1~10, 기본 5 |

## 4. 응답 (200)

```jsonc
{
  "matches": [
    {
      "courseId": 1,
      "score": 0.92,
      "matched": [
        "220V 전용 콘센트 2구",
        "기가 유선망",
        "일 평균 방문객 480명 (요청 300명 이상)"
      ],
      "concerns": [
        "피크타임(11~14시)에는 실증할 수 없습니다"
      ],
      "reason": "전원과 네트워크 조건을 모두 갖췄고 방문객 규모도 요청을 넘습니다. 다만 점심 시간대는 피해야 합니다."
    }
  ],
  "summary": "전원과 네트워크 조건을 만족하는 현장 3곳을 찾았습니다.",
  "model": "claude-sonnet-4",
  "elapsedMs": 2140
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|:---:|---|
| `matches` | array | O | 빈 배열 허용. `score` 내림차순 정렬해서 주세요 |
| `matches[].courseId` | integer | O | 슬롯 제목·가격은 프론트가 이미 가진 목록에서 붙입니다 |
| `matches[].score` | number | O | **0~1로 정규화**. 화면이 백분율로 보여줍니다 |
| `matches[].matched` | string[] | O | 빈 배열 허용. 한 항목 40자 이내 권장 |
| `matches[].concerns` | string[] | O | 빈 배열 허용 |
| `matches[].reason` | string | O | 2~3문장 |
| `summary` | string | O | 결과 전체에 대한 한 문장 |
| `model` | string | O | 어떤 모델로 판단했는지 |
| `elapsedMs` | integer | O | 소요 시간 |

### 설계 의도

**`matched`/`concerns`는 배열, `reason`은 문장 — 둘 다 필요합니다.**
화면이 두 가지를 다르게 그립니다. 배열은 항목별 체크 표시로, `reason`은 문단으로
렌더링합니다. 문장만 오면 어디가 맞았는지 강조할 수 없고, 배열만 오면 왜 그런지
설명이 되지 않습니다.

**`concerns`가 이 기능의 핵심입니다.**
좋은 점만 나열하면 광고로 읽히고, 규칙 기반으로도 흉내낼 수 있습니다.
**안 맞는 점을 짚어주는 것은 텍스트를 실제로 이해해야만 가능**하며,
사용자가 판단할 근거도 여기서 나옵니다. 걸리는 점이 없으면 빈 배열로 주시고,
**키 자체를 빼지는 말아 주세요.** 프론트가 매번 방어해야 합니다.

**`courseId`만 주세요.**
프론트는 이미 `GET /api/courses`로 91건을 전부 가지고 있습니다. 제목·가격·산업군을
다시 실어 보내면 응답만 무거워지고, 두 곳의 값이 어긋날 여지가 생깁니다.

**`score`는 반드시 0~1입니다.**
모델이나 점수 산식을 바꿔도 화면이 깨지지 않습니다.

**`model`·`elapsedMs`는 시연용이 아니라 근거용입니다.**
"AI가 실제로 돌았다"를 화면에서 보여줄 수 있고, 나중에 결과를 재현·감사할 때 씁니다.

## 5. 오류 계약

**이 표가 이 문서에서 가장 중요합니다.** 정상 응답보다 오류 처리에서 화면이 깨집니다.

| 코드 | 상황 | 응답 본문 | 프론트 동작 |
|---|---|---|---|
| 400 | `query` 없음 / 공백뿐 | `{"detail": "..."}` | 입력창에 오류 표시 |
| 401 | 토큰 없음 / 만료 | — | 세션 만료 안내 |
| 422 | `query` 1000자 초과 | `{"detail": "..."}` | 글자수 안내 |
| 429 | 호출 한도 초과 | `{"detail": "...", "retryAfterSec": 30}` | 재시도 시각 안내 |
| 503 | AI 제공자 장애 · 타임아웃 | `{"detail": "..."}` | **기존 규칙 기반 추천으로 폴백** |

**503 폴백을 계약에 넣어 둔 이유:** 시연 도중 외부 AI 호출이 실패해도 화면이 비지
않아야 합니다. 이 경우 프론트는 `GET /api/recommend/{userId}`(기존 규칙 기반) 결과를
"AI 없이 고른 추천"이라고 명시해 보여줍니다.

**타임아웃은 서버에서 끊어 주세요.** 프론트는 20초에서 포기합니다.
그보다 오래 걸릴 것 같으면 503을 주는 편이 낫습니다.

## 6. 프론트 연동 상태

현재 프론트는 **스텁으로 완전히 동작합니다.** 91개 슬롯 설명문을 실제로 훑어
`matched`/`concerns`/`score`를 만들기 때문에, 아무 문장이나 입력해도 반응합니다.

실제 API로 전환하려면 환경변수 하나만 주면 됩니다.

```bash
# vue-frontend/.env
VITE_MATCH_API=1
```

이 값이 있으면 `POST /api/recommend/match`를 호출하고, 없으면 스텁을 씁니다.
**프론트 코드는 고칠 필요가 없습니다.**

응답 형식이 위 명세와 다르면 화면이 조용히 비니, 필드명과 `score` 범위만
맞춰 주시면 됩니다.

## 7. 참고 — 구현 힌트

필수는 아니지만 도움이 될 만한 것들입니다.

- **슬롯 전체를 매번 모델에 넣지 마세요.** 91건 × 평균 56자면 지금은 괜찮지만
  확장되지 않습니다. `categories`·`budget`으로 먼저 후보를 줄이고
  (기존 `GET /api/courses/internal/recommend` 재사용 가능), 남은 것만 모델에 넘기세요.
- **`concerns`를 반드시 만들게 하세요.** 프롬프트에서 명시하지 않으면 모델은
  좋은 말만 씁니다. "맞지 않는 점을 최소 하나 찾되, 정말 없으면 빈 배열"처럼
  지시하는 편이 안정적입니다.
- **`courseId`는 반드시 실제 존재하는 id여야 합니다.** 모델이 지어낼 수 있으므로
  응답을 돌려주기 전에 후보 목록과 대조해 걸러 주세요.
- **평가 데이터를 함께 넣으면 좋습니다.** `review-service`의
  `GET /api/reviews/user/{hostId}/reputation`은 인증 없이 조회됩니다.
  호스트 평판을 근거에 넣으면 `reason`이 훨씬 설득력 있어집니다.
